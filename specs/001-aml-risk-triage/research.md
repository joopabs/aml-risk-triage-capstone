# Phase 0 Research: Explainable AML Transaction-Risk Triage

**Date**: 2026-09-04 | **Plan**: [plan.md](plan.md) | **Spec**: [spec.md](spec.md)

Every Technical Context item that could have been marked NEEDS CLARIFICATION is resolved
below. Where a decision depends on dataset facts, the fact is labeled **expected** (from public
PaySim documentation) and tied to the spec validation task that confirms it. Nothing here
asserts a dataset statistic or model result as fact.

## R-01: Python environment and dependency pinning

- **Decision**: Python 3.11.12 via pyenv (`.python-version`), virtualenv at `.venv`, top-level
  dependencies in `requirements.in` / `requirements-dev.in` / `requirements-api.in`, pinned
  lockfiles generated by `uv pip compile` into `requirements*.txt`, installed with
  `uv pip sync`. `pyproject.toml` declares `requires-python = ">=3.11,<3.12"` and holds ruff,
  pytest, and coverage config. The package is installed editable (`pip install -e .`) so
  notebooks import `aml_triage`.
- **Rationale**: 3.11.12 is installed locally and is the requested version; `uv` is present and
  produces deterministic pins fast; the constitution requires a pinned `requirements.txt`, which
  the compiled lockfile satisfies while `.in` files stay readable. Separate API pins keep
  optional work import-isolated (P XI).
- **Alternatives considered**: Poetry/PDM (extra tool, lockfile not a plain requirements.txt);
  conda (not installed; heavier); a single unpinned requirements.txt (violates G3).

## R-02: Data acquisition path

- **Decision**: `scripts/fetch_data.sh` tries the Kaggle API (`kaggle datasets download
  ealaxi/paysim1`) only when `KAGGLE_USERNAME`/`KAGGLE_KEY` are present in the environment or
  an untracked `.env`; otherwise it prints manual-download instructions and waits for the file
  in `data/raw/`. In both paths it verifies SHA-256 against `configs/data_source.yaml` and
  refuses to proceed on mismatch. The first successful download records `sha256`,
  `downloaded_on`, `license_text_verbatim`, and `license_verified_on` into
  `configs/data_source.yaml` and `data/README.md` (spec V1).
- **Rationale**: The Kaggle CLI is not installed and requires an account token, which must never
  be committed (FR-014). A manual path keeps the pipeline reproducible for reviewers without
  Kaggle credentials. Checksum pinning prevents silent dataset substitution.
- **Alternatives considered**: committing the CSV (violates FR-013, size); mirroring to a
  personal bucket (redistribution may violate license, adds credentials); `kagglehub` (same
  credential requirement, adds dependency).

## R-03: Model library choices

- **Decision**: Candidates from `configs/models/`: `DummyClassifier(strategy="prior")`;
  `LogisticRegression(class_weight="balanced", solver="saga" or "lbfgs")` with scaling;
  `imblearn.ensemble.BalancedRandomForestClassifier`; scikit-learn
  `HistGradientBoostingClassifier(class_weight="balanced")`. XGBoost is recorded as a drop-in
  alternative for the boosting slot, enabled by a config switch if installed, but is not in
  `requirements.in`. Deep learning is excluded.
- **Rationale**: All four are in the user's preferred stack (scikit-learn, imbalanced-learn).
  `HistGradientBoostingClassifier` handles millions of rows quickly, supports `class_weight`,
  and is supported by `shap.TreeExplainer`. Balanced RF is the project decision's named model.
  Deep learning offers no expected benefit on a small-column tabular problem and would add
  reproducibility burden; the constitution requires written justification for it, recorded
  here.
- **Alternatives considered**: XGBoost/LightGBM (fine, but extra dependency; kept optional);
  SVM (poor scaling to millions of rows, rubric lists it only as an example); calibrated
  isolation forest (unsupervised, not the task).

## R-04: Dataset scale and memory strategy

- **Decision**: Load the raw CSV once with an explicit dtype map (`float32` for amounts and
  balances, `category` for `type`, `int16`/`int32` for `step`, `int8` for labels), write
  parquet splits with pyarrow, and operate on parquet thereafter. Hyperparameter search uses a
  seeded stratified subsample of the training split (size in config, default `tune_sample_rows`
  to be set after profiling), while every final fit uses the full training split and every
  evaluation uses the full validation or test split. SHAP global explanations use a seeded
  sample of test rows and a seeded training background sample.
- **Rationale**: PaySim is **expected** to be on the order of several million rows and eleven
  columns (spec V3 confirms). With dtype downcasting this fits well under the 12 GB constraint
  on the 16 GB machine. Search on a subsample keeps M6 within the 20-minute budget while
  keeping selection and reporting on full data.
- **Alternatives considered**: Polars/Dask (not in preferred stack; unnecessary at this scale);
  full-data tuning (too slow for iteration); subsampling the test set (would weaken the
  headline metrics; rejected).

## R-05: Split design and review period

- **Decision**: Temporal split on `step` with boundaries `train_end_step` and `val_end_step`
  chosen after profiling positives per step so that each split contains enough positives for
  stable PR-AUC (target set in config after V4/V9; a minimum positive count per split is
  enforced by `split.py`). The review period for Recall@K is `review_period_steps`, **expected**
  24 (PaySim documents `step` as one hour over roughly one month; spec V8 confirms). Recall@K
  is computed per review period in the evaluation split and reported as the mean across
  periods plus a pooled figure. Fallback: if later steps lack positives, switch to stratified
  split and drop all time-aggregate features, per FR-041, with the change logged in
  `split_manifest.json` and the report.
- **Rationale**: Temporal ordering is the only defensible way to honor prediction-time
  assumptions and causal aggregates. Per-period Recall@K mirrors the operational question
  ("what does an investigator get out of today's K reviews").
- **Alternatives considered**: random stratified split as primary (leaks future aggregates,
  overstates performance); grouped split by account (PaySim accounts are **expected** to be
  mostly single-use, making grouping uninformative; V3/V10 confirm); rolling-origin CV
  (valuable but heavier; may be added for the selected model only if time permits).

## R-06: Post-transaction balance fields and the prediction-time policy

- **Decision**: PaySim is **expected** to carry pre- and post-transaction balances for origin and
  destination. The scoring context is defined as end-of-period batch triage, in which posted
  balances are available, so post-transaction-derived features (balance deltas, balance-
  arithmetic inconsistency flags) are permitted but tagged `available_at_prediction_time:
  batch_only` in the feature registry. Two feature sets are evaluated: `primary` (includes
  batch-only features) and `strict_pretx` (excludes them). Both appear in the model comparison
  as an ablation; the report discusses the gap as evidence of simulator artifacts if large. The
  rule-flag column (**expected** `isFlaggedFraud`) is never a feature; it defines the rule
  comparator. Raw account identifiers are never features.
- **Rationale**: The spec requires exclusion or explicit justification for post-transaction
  state. Batch triage is the honest framing of the intended decision, and the ablation exposes
  how much lift comes from simulator behavior rather than transferable signal (risk R3).
- **Alternatives considered**: exclude all post-transaction fields (loses domain features the
  project decisions call for, and misrepresents the batch setting); include without ablation
  (hides leakage-like artifacts).

## R-07: Causal aggregate features

- **Decision**: Compute per-origin and per-destination prior-transaction count and sum of
  amount using a stable sort on (`step`, original row index), groupby cumulative sum, and a
  shift of one row within the group, so each row sees only strictly earlier rows. Same-step
  ordering is by original row index and this limitation is documented. Aggregates are computed
  on the concatenated ordered data but only "look backward", so no fitting is involved; a
  brute-force test on the fixture verifies equality. Aggregates are kept only if V10 shows
  they carry signal.
- **Rationale**: Satisfies FR-032 without leakage; cheap to compute at scale.
- **Alternatives considered**: time-windowed rolling features (adds complexity; step
  granularity is coarse); target encoding of accounts (leakage-prone; rejected).

## R-08: Feature selection and PCA methods

- **Decision**: Two selection methods, both as pipeline steps fitted on training rows: a filter
  (`SelectKBest` with mutual information, k set in config) and an embedded method
  (L1-penalized logistic regression coefficients via `SelectFromModel`). The `selected` set is
  the intersection-with-fallback (union if intersection is too small; rule in config). PCA is
  fitted on standardized numeric features of the training split for scree/variance reporting
  and a 2-D label-colored projection; a `pca_variant` feature set (top components) is run for
  one candidate as a documented experiment. The selected model is expected to use raw
  engineered features; the PCA report states its role explicitly (FR-035).
- **Rationale**: Meets "at least one" with two complementary methods and gives PCA a stated,
  honest role rather than forcing it into the final model.
- **Alternatives considered**: RFE wrapper (expensive on millions of rows); tree importances
  alone (biased toward high-cardinality numerics; used as a cross-check only).

## R-09: Imbalance handling, calibration, and operating point

- **Decision**: Class weighting is the default for all three candidates; an `imblearn.Pipeline`
  variant with `RandomUnderSampler` on the training fold is run for the boosting model as a
  documented comparison, ensuring resampling happens inside `fit` only. Calibration is
  assessed with reliability curves, Brier score, and expected calibration error (10 bins). If
  isotonic calibration fitted on the validation split improves Brier without reducing PR-AUC
  or Recall@K beyond a config tolerance, it is applied as a `CalibratedClassifierCV(cv="prefit")`
  wrapper; otherwise the uncalibrated model is kept and the decision is logged. The operating
  point is the top-K rule at the primary K, plus a probability threshold chosen on validation
  to maximize F2 (recall-weighted) for confusion-matrix reporting; both are frozen in
  `configs/operating_point.yaml` before test is unlocked.
- **Rationale**: Ranking is the objective, so K-based operation is primary; a threshold is
  still needed for confusion-matrix metrics required by the spec. Validation-only calibration
  and threshold selection preserve single-touch test.
- **Alternatives considered**: SMOTE (synthetic rows on continuous balances create implausible
  transactions; kept out of the primary path); Platt scaling (isotonic is more flexible with
  ample validation data).

## R-10: Recall@K definition and tie-break

- **Decision**: For each review period p in the evaluation split with positives P_p and top-K
  set T_p (K from config, K_p = min(K, |rows in p|)), Recall@K_p = |T_p ∩ positives| / |P_p|
  (periods with zero positives are excluded from the mean and counted separately);
  Precision@K_p = |T_p ∩ positives| / K_p. Report the mean over periods, the pooled value over
  the whole split, and the distribution. Tie-break for equal scores: earlier `step` first, then
  lower original row index. Random ranking comparator uses the global seed; the rule comparator
  ranks flagged rows first, then by amount descending. The illustrative KPI is the mean number
  of simulated-fraud transactions in T_p and the ratio of that to the random and rule
  comparators. The dummy comparator emits constant scores, so its ranking equals the
  tie-break order (chronological); random ranking is therefore the primary null hypothesis
  and the dummy comparison is reported as "chronological order" in tables.
- **Rationale**: Deterministic, mirrors the daily capacity question, and handles short periods
  (edge case in spec).
- **Alternatives considered**: global top-K over the whole test split only (ignores daily
  capacity; kept as the pooled secondary figure).

## R-11: Report and deck tooling

- **Decision**: Final report authored in Markdown, assembled from generated section files by
  `report_builder.py`, exported to PDF by `scripts/export_report.sh` using pandoc if present,
  otherwise via a documented fallback (browser print-to-PDF of rendered Markdown, or
  `nbconvert --to webpdf` of a wrapper notebook). Technical deck is
  `notebooks/90_technical_deck.ipynb` exported with `jupyter nbconvert --to slides` (reveal.js
  HTML) and to PDF for submission. Business deck is built in PowerPoint, Canva, or Google
  Slides from the committed `business_deck_outline.md`, exported to PPTX and PDF.
  `scripts/check_slide_counts.py` enforces 8–12 slides on both.
- **Rationale**: Matches the assignment's format guidance (Jupyter slides for technical,
  PowerPoint/Canva for business), keeps the technical deck reproducible from code, and keeps
  submission formats approved.
- **Alternatives considered**: LaTeX Beamer (permitted but adds a TeX toolchain); Marp
  (not listed by the assignment); python-pptx generation of the business deck (possible later
  enhancement; manual authoring is faster for a 8–12 slide executive deck).

## R-12: Secret scanning and quality tooling

- **Decision**: `pre-commit` (pip-installed into the dev environment) with hooks: `ruff`,
  `ruff-format`, `detect-secrets` (with committed `.secrets.baseline`), and `nbstripout` for
  notebooks. GitHub Actions CI runs `ruff`, `detect-secrets-hook`, `pytest`, and a smoke
  pipeline on a seeded sample produced by `scripts/make_sample.py` from a small synthetic
  fixture (not PaySim rows, so CI needs no dataset download). A `git status` check in
  `make ci` fails if any file under `data/raw` or `data/processed` is tracked.
- **Rationale**: pre-commit is not installed globally but is trivial to add as a dev
  dependency; detect-secrets is lightweight and Python-native; nbstripout prevents large,
  data-bearing notebook outputs from being committed.
- **Alternatives considered**: gitleaks (binary install; fine but non-Python); committing
  executed notebooks (outputs may embed data rows; instead, figures are saved to `reports/`
  and notebooks stripped).

## R-13: Reproducibility tolerance

- **Decision**: `set_global_seed` seeds `random`, `numpy`, and passes `random_state` to every
  estimator, sampler, splitter, and search. Thread counts for boosting and RF are fixed via
  config (`n_jobs`) and `OMP_NUM_THREADS` in the Makefile. `reproduce-check` fits the selected
  model twice and diffs metrics; if any metric differs, the maximum absolute difference is
  recorded in `README.md` as the tolerance (spec V13). Target is exact equality.
- **Rationale**: Tree ensembles with multithreading can be non-deterministic in float
  reductions; measuring rather than assuming keeps the claim honest.
- **Alternatives considered**: forcing single-thread everywhere (slower; used only if the
  measured tolerance is unacceptable).

## R-14: Optional work boundaries (Steps 8 and 9)

- **Decision**: Optional work starts only after gates G1–G11 are evidenced. The FastAPI service
  lives in `aml_triage.api`, depends on `requirements-api.txt`, loads `models/LATEST`, and
  exposes `GET /health` and `POST /score` per `contracts/scoring-api.yaml`. Docker image built
  from `deployment/Dockerfile` copies `src/`, `configs/`, and the selected `models/<version>/`
  bundle only. MLflow is documented as a recommended tracker in `docs/mlops_plan.md` but not
  wired in by default. GenAI usage, if any, is logged in `docs/genai_usage.md` as it happens,
  including this Spec Kit workflow's assistance, with human review noted.
- **Rationale**: Protects core deliverables (risk R9), keeps optional dependencies isolated
  (P XI), and makes the bonus work transparent (G12).
- **Alternatives considered**: Flask/Dash (permitted; FastAPI chosen for pydantic schemas that
  double as contracts); cloud deployment (out of scope).
